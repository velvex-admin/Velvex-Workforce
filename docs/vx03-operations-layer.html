01

What this is

A single Cloudflare Worker running thirteen agents against a Supabase database. No agent framework, no ORM — plain fetch against PostgREST and a thin wrapper over the Messages API. The whole system is one deployable artifact.

The dashboard is served at /x/<APP_PATH_SECRET>/. There is no authentication by explicit decision: access control is an unguessable URL. The single choke point for adding real auth later is authorize() in src/index.ts — nothing else in the codebase decides who may call it.

02

The autonomy model

This is the idea the whole system is built around. An agent never acts directly — it proposes, and the boundary decides what happens next. Order matters, because vetoes resolve before allowances.

1Agent proposesDraft this post, publish that draft, reply to this comment, flag this stalled lead.
2Approval rules run first — as vetoesIf any fires, the action is queued. Full stop. Spend, irreversibility, a new channel, pricing changes, anything new by type.
3Routine rules run second — as allowancesOnly reached when no veto fired. Drafting inside approved pillars, publishing a ready draft in an established slot.
4Unmatched, or a failed judgement callQueued. The default is deny, and uncertainty escalates rather than proceeding.
→Executes now, or waits for youRoutine work runs and lands in Completed. Everything else lands in Pending until you approve or reject it.
Routine — runs unattended

Drafting inside approved pillars and formats, in the voice profile. Publishing a ready draft when a scheduled slot is due. Applying non-protected site fixes. Replying to praise and simple questions above the confidence floor.

Needs approval — always

Every growth idea, by definition. Engaging a named external account. Any paid promotion. A campaign type nobody has run. Copy that never cleared the drafting rule. Anything touching a protected page.

No agent module calls a connector directly. That is what keeps this line real rather than a comment in a file.

04

Channel strategists

The architecture document originally scoped these as timing-and-publishing only. That was widened deliberately: each channel now owns its platform end to end.

Every time a strategist wakes it reads its own past posts and channel memory, drafts one post written for that specific platform, and proposes up to three growth ideas — which always queue, by design. It publishes only when a scheduled slot is genuinely due.

Learning from past posts explicitly does not mean copying them. The prompt instructs the model to notice what landed and what stalled, break the pattern when recent posts all opened the same way, and rewrite any draft that could sit unnoticed inside the recent list.

LinkedIn was scoped as an external build in the original document. That was overridden — the strategist is ours. Publishing still routes through the partner queue because we hold no LinkedIn API credentials; switching to direct posting later is deleting one option.

05

How scheduling actually works

Three separate concepts get confused with each other. They are not the same thing.

ConceptLives inWhat it decides
Cronwrangler.tomlWhen the Worker wakes at all. Three schedules only: hourly on the hour, 07:00 UTC daily, 08:00 UTC Mondays.
Cadenceper agentWhich tick wakes that agent. This is the hourly / daily / weekly label on each dashboard node.
Weekly plancore/schedule.tsWhen posts actually go out. Three slots per channel per week, re-rolled every week.

A strategist wakes hourly but posts three times a week

Waking keeps the draft shelf stocked — if fewer than three finished drafts are waiting, it writes one, and nothing goes public. Publishing is gated separately by the weekly plan. Slot times are drawn from a generator seeded on the channel and ISO week, so they are stable within a week (a restart never reshuffles a week that is half published) but different between weeks, so nothing lands on a repeating on-the-hour pattern that reads as automated.

Windows target English-speaking audiences: X Monday to Friday, 12:00–21:00 UTC; LinkedIn Tuesday to Thursday, 13:00–21:00 UTC. Run once on the dashboard fires a wake-up immediately but will not publish early — it still checks whether a slot is due.

06

The dashboard

A pan-and-zoom canvas rather than a scrolling page, because the system is a network and not a workflow. The Chief-of-Staff sits on the left with two sub-nodes — Completed and Pending — with animated lines running from each section into it. Marketing, Sales and Executive sections hold their agent dots on the right.

Drag to pan, wheel to zoom, click any node to open its panel, Escape to close. Each panel carries that agent's routine and approval rules, its recent activity, a Run once control, and cadence override buttons — hourly, daily, weekly, paused, or default. Overrides persist in the database and take effect with no redeploy.

Feeding it business data. Pipeline and finance figures are not read from anywhere — they are pushed in. PUT /api/state/<key> with a JSON body writes a typed snapshot the agents then reason over. GET /api/state lists the keys it understands.

Live thought trails. The runner captures every line an agent emits while working and writes it to a status board. A running agent shows an amber pulsing ring and its current phase; its panel shows what it is doing right now plus the last twelve steps. When idle, the panel shows the previous run's trail, so there is always an answer to "what did it just do". The page polls every three seconds while anything is running and every sixty otherwise.

08

Traps already paid for

Never set variables in the Cloudflare dashboard

wrangler.toml is the source of truth. Every deploy overwrites whatever the dashboard says, so a value changed in the web UI is silently stamped back on the next deploy. This turned enabling X publishing into a loop that repeated several times before the cause was found. Edit the file, deploy, commit. Secrets are the opposite — those live only in wrangler secret put and never in the file.

  • A failing Cloudflare build complaining about a missing index.js is a red herring. That is Cloudflare's server-side builder trying to build the repo itself and looking for a plain JS entry point. Our entry is TypeScript, compiled by wrangler at deploy time. It has never been the path that deploys this Worker, and its failures never touch what is running.
  • Haiku rejects thinking and effort parameters. Sending either returns a 400. The request builder is capability-aware and omits them per model.
  • The API rejects array length constraints in output schemas. A single maxItems silently broke drafting on all three strategists — the request failed before the model ran, so it cost nothing, produced nothing, and surfaced only as a logged error. A test now walks the real schema objects and fails the build on any rejected keyword.
  • The FAQ page is a pricing page. It is protected from unattended SEO edits for that reason.
09

Still open

These were flagged during the build and remain unresolved. None of them blocks the system running — each one has a defined holding behaviour rather than a guess.

How does the SEO agent write to the site? The architecture document grants write access but names no platform. The site is a static build on Netlify, which narrows it to a commit against the site repository or the Netlify API. Until that is decided the agent still runs in full and writes every proposed edit out completely — page, exact before, exact after — into a change queue. Real work is already waiting there.
Where do the pipeline and finance figures come from? Both live in Phase 0 systems this project must not touch, and no read path was specified. There is a push endpoint instead: PUT /api/state/<key>, which n8n or anything else can post to on a schedule. Until data arrives, each agent reports that it has none rather than inventing a number.
Ops-Health has nothing to watch It needs a read-only operations status endpoint at OPS_PIPELINE_STATUS_URL. No Phase 0 credentials are wired into this project, deliberately. Until that URL exists the agent is dormant.
The voice profile is a default, not your writing A deliberately non-generic default is in place in one swappable file, with mechanical checks that catch stock cadences and engagement bait before a draft can reach a channel. Moving to your own writing samples later means replacing that single file, not retraining anything.

Where the memory lives

None of the context behind these decisions survives a chat ending. It is written into CLAUDE.md at the repo root instead, which Claude Code loads automatically at the start of every session in this repository.

It records what cannot be recovered by reading the code: the business grounding and pricing, which parts of the original architecture document were deliberately overridden and why, the reasoning behind each model tier, the agents that were considered and declined so they do not get re-proposed, and every trap above. Keep it current — when a decision is made or a trap is found, it belongs there.
